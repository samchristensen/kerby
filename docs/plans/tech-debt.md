# Tech debt

One line each: what, why it matters, what fixes it. Remove the line in the commit that pays it. Plan
[0003](done/0003-tech-debt.md) schedules every line.

- The import scanner in `check-architecture.ts` is regex-based and also reads strings in comments. Replace it with a parser if a false positive appears.
- `AgentRuntime` has one adapter and no conformance suite. Write the suite when the second adapter lands.
- A conversation read and a turn's rehydrate fetch each message body from S3, one request per message (a page, or the history budget, at a time). Add a per-process body cache when a profile shows it (plan 0003, parked "Body cache").
- Alert debounce is per process: with several worker replicas a storm posts once per replica per five minutes. Share the window (a control-database row) if replicas grow.
- No edge proxy or WAF in front of `api`: an install keeps it on its private network unless something outside calls it. Request and failed-auth limits are token buckets in each api process (N processes allow N times `requestsPerMinute`), and with `TRUST_PROXY=true` the failed-auth limit trusts the left-most `X-Forwarded-For`, which Railway does not publish as a contract. Move both to an edge or a shared counter if an install is exposed publicly at scale.
- Model keys (ADR 0008): no automated re-seal, so `KERBY_SECRET_KEY` cannot be rotated (ADR 0024): every key derives from it. Write the re-seal (open with the old derived keys, seal with the new, then restart) when the first rotation is needed.
- The console (ADR 0014, amended by 0024) has one account, the configured admin, with no second factor; a forgotten password is a change to `KERBY_ADMIN_PASSWORD` and a restart. Its sign-in limits are per process, and the per-account limit refuses even the right password once spent, so whoever can reach the console and knows the admin email can keep the admin out for an hour at a time (API keys keep working). Add a second factor before a console is exposed to the internet beyond its owner.
- An open event stream keeps its tenant's pool (2 connections) leased on that api process besides the shared listener, so an api process holds 3 connections per distinct streaming tenant (capped through `MAX_STREAMS_PER_PROCESS`, 60; docs/deploy.md#postgres). If streams outgrow the budget, read through a short lease per poll so only the listener stays open.
- Stored bytes are capped (`limits.storageBytes`) but not reported to `usage`; meter them with billing (plan 0001, M8, parked by ADR 0024).
- The storage quota sums the tenant's whole blob index and prompt tables (`storedBytes`), twice per post: a cost that grows with the tenant's history, bounded only by `limits.storageBytes`. Keep a running total (a row kept by triggers) when a profile shows it in post latency (plan 0003, parked "Stored-bytes total").
- Live events (text deltas, tool events) ride `pg_notify` in the tenant's database, and every committing `NOTIFY` takes one lock for the whole cluster (docs/deploy.md#postgres), a point where tenants' streaming contends. Move them to a message bus (Redis pub/sub behind one package; an ADR, since Postgres is the only service) when waits on that lock show up, or with the shared counters once `api` runs more than one process (plan 0003, parked "Live events bus").
- Tenant limits (`tenants.limits`) change only by SQL; there is no endpoint or setting for them.
- The console's chat renders plain text and cannot delete or rename conversations; conversations older than titles show as "Untitled chat"; a new chat whose first post is refused (storage quota) leaves an empty conversation; the console's calls share one address in the api's failed-authentication limit (no `X-Forwarded-For` on the private network). Fixed when a tenant asks (plan 0003, parked "Chat gaps").
- Prompts (ADR 0017): a published prompt cannot be deleted or renamed, there is no diff between versions, no saved test cases for decision models, and only one person edits at a time (a stale save is a 409, not a merge). In the rich editor an XML-like tag typed as text is saved escaped (`\<tag>`); the hint says to write tags in Markdown mode. Build each when a tenant asks.
- Chat search (ADR 0021) has no approximate-nearest-neighbour index: a semantic search scans the tenant's embedded chunks exactly. Add a per-model HNSW expression index (`(embedding::halfvec(<dims>))`, partial on `embedding_model`) when a tenant passes 100 000 chunks or `search completed` shows over 500 ms.
- Chat search keeps each semantic search's query in the tenant's `absurd.t_search` for Absurd's retention (30 days), and a semantic search waits on a worker round trip (about 35 ms locally, plus the provider). Shorten the `search` queue's `cleanup_ttl`, or embed queries somewhere that can open keys without a task, if a tenant asks.
- The `kerby` image carries the console's dependencies (`next`, `@next`, `@milkdown/*`: about 300 MB unpacked) though `pnpm install --prod --filter @kerby/kerby...` selects no console workspace (`pnpm ls --filter` lists none); the images CI built before ADR 0024 did too. Find why the filtered install (with `nodeLinker: hoisted`) pulls them and trim it, since every install pulls the image.
- A new SDK version shows on the npm registry about five minutes after `npm publish` (observed for 0.1.0 and 0.1.1: `npm view` and a direct registry read both listed the old versions meanwhile). Two merges to `main` that change the SDK inside that window make the second `sdk` job read a stale list and try to publish the same version, which npm refuses: rerun the job. Make `scripts/sdk.ts publish` wait for its version to appear, or hold the second merge, if it happens.
- The tenant database role's connection limit (20) is a constant in `packages/db/src/cluster.ts` that control re-applies at every start, so an install that runs more than about ten busy api and worker processes cannot raise it (docs/deploy.md#running-the-roles-separately; measured 12 of 20 right after a turn with 7 processes up, not tested at the limit). Make it a control setting when one does.
