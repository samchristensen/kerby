# Tech debt

One line each: what, why it matters, what fixes it. Remove the line in the commit that pays it. Plan
[0003](active/0003-tech-debt.md) schedules every line.

- The import scanner in `check-architecture.ts` is regex-based and also reads strings in comments. Replace it with a parser if a false positive appears.
- `AgentRuntime` has one adapter and no conformance suite. Write the suite when the second adapter lands.
- A conversation read and a turn's rehydrate fetch each message body from S3, one request per message (a page, or the history budget, at a time). Add a per-process body cache when a profile shows it (plan 0003, parked "Body cache").
- Alert debounce is per process: with several worker replicas a storm posts once per replica per five minutes. Share the window (a control-database row) if replicas grow.
- Bucket backup (ADR 0013): message bodies can lose up to a day (nightly copy), copies pass through control (each bucket has its own keys, so no server-side copy), and a control down the whole day alerts only through Railway's deployment webhook (it has no public domain, so no outside check reads its freshness alarm).
- CI's `RAILWAY_TOKEN` (production project token) can read every production variable, so every secret, and the bucket credentials (measured, plan 0003 C4). Same-repository pull requests get it in `railway-plan`, so anyone who can push a branch can read production secrets through a workflow change, as anyone who can merge already could through `release`. If more people get write access: put both secrets behind a GitHub environment limited to `main` and drop the plan on pull requests, or require review before merge.
- No edge proxy or WAF in front of `api` (the owner's call, 2026-11-22: not yet). Request and failed-auth limits are token buckets in each api process: N processes allow N times `requestsPerMinute`, and the failed-auth limit trusts Railway's `X-Forwarded-For` (left-most), which Railway does not publish as a contract. Move both to the edge or a shared counter when the api scales out or an edge lands.
- IaC and buckets: an orphan bucket named `modular-safe-wx5G` was left in the project by a trial. It has no instance, so the dashboard does not list it, `railway bucket delete` refuses it (and so does a patch that adds an instance), and the public API has no bucket deletion. It holds no data. Retry the delete when the `railway` pin is bumped (plan 0003, parked "Orphan bucket"), or ask Railway support.
- Model keys (ADR 0008): no automated re-seal after a secrets key rotation (re-`PUT`, or write a script when the first rotation happens).
- The console (ADR 0014) has open sign-up with no email verification, password reset, CAPTCHA, second person per tenant or second factor, and its sign-up and sign-in limits are per process. A forgotten password needs an operator (a new `password_hash` from the console's `hashPassword`, by SQL). Add verification and reset (an email provider) before the console is advertised, and a shared counter or an edge when it runs more than one process.
- An open event stream keeps its tenant's pool (2 connections) leased on that api process besides the shared listener, so an api process holds 3 connections per distinct streaming tenant (capped through `MAX_STREAMS_PER_PROCESS`, 60; docs/deploy.md#postgres). If streams outgrow the budget, read through a short lease per poll so only the listener stays open.
- Stored bytes are capped (`limits.storageBytes`) but not reported to `usage`; meter them with plan 0001, M8.
- Tenant limits are set only at provisioning; there is no operator endpoint to change them (SQL until plan 0001, M9).
- The console's chat renders plain text and cannot delete, rename or search conversations; conversations older than titles show as "Untitled chat"; a new chat whose first post is refused (storage quota) leaves an empty conversation; the console's calls share one address in the api's failed-authentication limit (no `X-Forwarded-For` on the private network). Fixed when a tenant asks (plan 0003, parked "Chat gaps").
